## Глава I

### Преамбула

Представь типичный ML-проект на ранней стадии: аналитик открывает Jupyter, за пару часов собирает прототип, показывает красивые графики – и на этом всё. Ноутбук отправляется коллегам, каждый правит его под себя, через месяц воспроизвести результат не может никто. Ячейки выполнены не по порядку, зависимости не зафиксированы, данные лежат «где-то рядом», а метрики считались на разных сплитах. Именно так рождаются проекты, которые «работают только на ноутбуке автора».

![jupyter](./misc/images/jupyter.png)

Production-ML начинается тогда, когда ноутбук превращается в **модульный пайплайн**:

- **Data** – чтение и очистка сырых данных из источников в одном месте, с фиксированными контрактами.
- **Features** – feature engineering через sklearn-совместимые трансформеры, которые можно переиспользовать
  и сериализовать вместе с моделью.
- **Model** – обучение отделено от подготовки данных, конфигурация гиперпараметров вынесена в YAML, запуск
  идёт через CLI.
- **Metrics и artefacts** – каждый запуск сохраняет логи, метрики и сериализованные модели в отдельную папку,
  чтобы эксперименты можно было сравнивать и катить в production.
- **Inference** – скрипт, который грузит сохранённую модель и считает предсказания на новых данных, живёт
  отдельно от обучения. В бою обучение и inference обычно запускаются разными сервисами.

![intro-pipe](./misc/images/intro_pipe.png)

Почему не Jupyter в production? [Причин](https://towardsdatascience.com/5-reasons-why-jupyter-notebooks-suck-4dc201e27086)
несколько: порядок исполнения ячеек ненадёжен, состояние легко «расходится», код сложно версионировать,
тестировать и деплоить. Jupyter – отличный инструмент для прототипа и EDA, но production-код пишется
модулями, покрывается тестами и запускается через CLI с конфигами.

Чтобы задание было максимально приближено к реальности, мы помещаем тебя в рабочую ситуацию. Полгода в компании шёл проект «предсказание удовлетворённости покупателя»: по данным о заказе – стоимости, доставке, категории товара – модель должна предсказывать оценку от 1 до 5, которую клиент поставит в отзыве. Бизнес хочет выгружать предсказания в CRM, чтобы служба поддержки заранее связывалась с покупателями, которые, скорее всего, поставят низкую оценку. Предыдущий разработчик успел собрать скелет: конфиги, пакетную структуру, тесты, линтер. Часть функций написана, часть – только сигнатуры с `# TODO`, а кое-где стоит `raise NotImplementedError`. Демо заказчику через два дня. Разбираться и дописывать придётся тебе.

## Глава III

### Цели

Довести проект коллег до состояния «можно катить в production» и обучить две baseline-модели:

- Linear Regression – быстрый и интерпретируемый baseline;
- Gradient Boosting Regressor – нелинейный ансамбль.

Обе модели решают одну задачу регрессии: по данным заказа предсказать `review_score` ∈ [1, 5]. Для бизнес-интерпретации мы дополнительно считаем **ROC-AUC по бинаризации**: позитивный класс – «покупатель доволен» (`review_score ≥ 4`). Это позволяет использовать регрессионные предсказания как score для ранжирования заказов по риску низкой оценки.

В этом проекте мы будем работать с частично подготовленным датасетом [Brazilian E-Commerce Public Dataset by Olist](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce).

Датасеты лежат в дополнительных материалах проекта - скачай их.

- **`olist_public_dataset.csv`** – заказы с атрибутами товара, доставки, оплаты и отзывом;
- **`product_category_name_translation.csv`** – перевод названий категорий товаров на английский.

Работая с этим проектом, ты научишься:

- собирать модульный ML-пайплайн: данные → признаки → модель → метрики → артефакты;
- гибко конфигурировать запуски;
- писать собственные шаги предобработки;
- разделять обучение и инференс, чтобы развёртывание модели выполнялось отдельным конвейером без повторного обучения;
- поддерживать качество кода тестами и линтером.

Основную работу ты будешь выполнять в Python-файлах внутри папки `src/`. Структура описана в `src/README.md`.

По итогам проекта в папке `artefacts/` должны лежать логи обучения, сериализованные модели и метрики
качества обеих baseline-моделей. Порог приёмки: **ROC-AUC > 0.65** для обеих моделей.

### Конфигурация проекта

Коллега выбрал для гибкой конфигурации проекта [Hydra](https://hydra.cc/docs/intro/) и
[dataclasses](https://docs.python.org/3/library/dataclasses.html).

Hydra собирает итоговый конфиг из YAML-файлов в `configs/`.

Любой параметр можно переопределить из командной строки. Пресеты датасета, признаков и модели
комбинируются без правок кода. Запуски воспроизводимы, сценарии переключаются одной командой.

Структуру и типы параметров задают `dataclass`-ы в `satisfaction/entities/`.
Hydra подгружает YAML в эти классы и проверяет поля.
Готовый объект конфигурации передаётся в `train_pipeline`.
Настройки в файлах и в коде не расходятся.

![hydra](./misc/images/hydra.png)

### Обработка признаков

(новые признаки из гипотез) и соберёшь общий `ColumnTransformer`.

### Обучение и инференс

В production обучение и inference (инференс) – это два разных процесса. Обучение запускается периодически, собирает
артефакты (модель, трансформер, метрики). Inference грузит артефакты и считает предсказания на новых
данных – уже без датасета для обучения и без sklearn-пайплайна «в коде». Поэтому важно сериализовать
трансформер отдельно от модели, чтобы на inference повторить ровно ту же подготовку признаков.

![inference](./misc/images/inference.png)

### Бонусное задание. MLflow

До сих пор метрики и артефакты обучения копились локально в папке `artefacts/` – удобно, пока
запусков единицы. Но когда экспериментов десятки (разные модели, гиперпараметры, кодировки), сравнивать
результаты по логам и JSON-файлам становится мучительно: какой запуск показал лучший ROC-AUC? с какими
параметрами? где лежит сериализованная модель?

[MLflow](https://mlflow.org/) решает эту задачу – это отдельный сервис, который принимает по HTTP API
метрики, параметры и артефакты каждого запуска и показывает их в UI. Любой запуск `train.py` становится
«run» в MLflow с полной воспроизводимой историей: параметры, метрики, ссылки на сериализованные модели.
Именно так устроен ML-tracking в большинстве production-команд.

![mlflow](./misc/images/mlflow.png)
